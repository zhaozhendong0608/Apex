# [B4] 线上排障与根因诊断 (B4-sop-troubleshoot)
> **触发**：`[B4]`/`排障`/`线上故障`/`OOM` ｜ **前置**：已部署环境 ｜ **产出**：根因 + 微创修复 + 防御单测

## 📌 核心目标
对已上线故障做标准化闭环：**先保现场 → 再取证 → 最后微创修复**，禁无头苍蝇式盲猜。

> 与 `[B3]` 的区别：`[B3]` 是本地开发期、代码未合主干；`[B4]` 是已部署真实故障，必须留现场证据并带防御单测。

## 🛡️ 3 铁律
1. **未取证不改码**：没查清真实日志与堆栈前，不许改核心业务代码。
2. **先保现场**：遇到 OOM / 高 CPU / 死锁 / 队列堵塞，**严禁先重启**；先做现场快照（线程转储、堆转储、Tail 日志）。
3. **修复必带防御单测**：必须补一条能稳定复现该故障的用例，验证红→绿后才可合并。

## 🧭 四步流水线
**Step 1 定级与影响面**：`P0` 崩溃/通信中断/DB 不可连；`P1` 接口 500/队列积压/权限异常；`P2` 页面渲染错/报表缺字段。确认是哪个服务、是否 Host 模式、是否刚发布过。

**Step 2 日志与链路穿透**
```bash
docker logs -f --tail=200 <container>
grep -C 5 "ERROR" /data/logs/app.log
```
判断是下游超时、拦截转换还是网络不可达（`Connection refused`）；区分业务抛错与基础设施故障。

**Step 3 性能深探**
```bash
top -Hp <pid>
jstack <pid> > jstack.dump
```
查队列积压（写入与读取游标差值）、消费者是否卡在持久化或锁竞争；确认监听地址是否误暴露外网。

**Step 4 微创修复 + 防重放**：最小修复（遵守 `[3]` 护栏 + TDD）→ 补复现单测 → 红变绿 → 走 `[4]`→`[6]`→`[7]`→`[9]`（必要时三级回滚）。

## 🧷 能力点
`C-B4-01` P0-P2 定级与影响面；`C-B4-02` 日志与链路穿透；`C-B4-03` 现场快照保证据；`C-B4-04` 线程/队列/网络深探；`C-B4-05` 微创修复 + 防御单测；`C-B4-06` 回滚衔接。
