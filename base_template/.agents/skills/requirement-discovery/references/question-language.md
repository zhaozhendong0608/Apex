# 技术问题白话转换

目标：AI 可以在内部使用专业概念，但用户收到的问题必须能凭业务经验回答。

## 通用转换表

| 内部关注 | 不要这样问 | 优先这样问 |
|---|---|---|
| 实时性 | 实时性指标是多少？ | 数据变化后，用户晚几秒看到还可以接受？ |
| 一致性 | 需要强一致还是最终一致？ | 同一份数据在两个页面短时间不一样，能不能接受？大概多久内要变成一致？ |
| 幂等 | 接口要不要幂等？ | 网络卡顿时用户连续点两次“提交/启动”，你希望只执行一次还是两次都算？ |
| 超时 | 超时时间是多少？ | 用户点了操作后，等多久还没回应就应该明确提示“没有成功”？ |
| 重试 | 重试策略是什么？ | 第一次发送失败后，系统要不要自己再试？还是必须让人确认后再试？ |
| 可用性 | SLA 是多少？ | 某个设备/外部系统临时连不上时，其他功能还能不能继续用？ |
| 降级 | 降级策略是什么？ | 某一部分坏了以后，是整个系统停下来，还是能先用剩下的功能？ |
| 缓存 | 是否需要缓存？ | 暂时拿不到最新数据时，可以先显示上一次的数据吗？如果可以，要不要明确告诉用户“这不是最新值”？ |
| 数据保留 | Retention policy？ | 半年前/一年前的数据以后还需要查吗？大概要留多久？ |
| 审计 | 是否需要 audit log？ | 以后出现问题时，要不要查到是谁、什么时候、改了什么？ |
| RBAC | 权限模型是什么？ | 哪些人只能看？哪些人能改？哪些危险操作只有少数人能做？ |
| 容错 | 容错要求？ | 其中一台设备或一个服务出故障时，其他设备/功能是否应该继续工作？ |
| 恢复 | RTO/RPO？ | 系统重启后，多久恢复使用可以接受？重启前的数据最多允许丢多少？ |
| 并发 | 并发用户多少？ | 大概会不会很多人同时操作？更接近几个人、几十个人还是几百人？ |
| 吞吐 | TPS/QPS？ | 高峰时大概每秒/每分钟会产生多少次操作或多少条数据？不知道精确值可给数量级。 |
| 数据质量 | 如何做质量标识？ | 页面上的“0”到底是真实值 0，还是可能只是没采到？用户需要分辨吗？ |
| 事件顺序 | 是否要求有序？ | 两条状态消息前后到反了，会不会导致业务判断错误？ |
| 去重 | 是否去重？ | 同一条告警/消息重复到两次，应该显示一次还是两次都保留？ |
| 补偿 | 补偿机制？ | 操作做到一半失败时，已经成功的那部分要撤回，还是保留并提示人继续处理？ |
| 审批 | 工作流审批？ | 哪些操作不能一个人直接执行，必须再由别人确认？ |

## 提问模板

优先使用：

“这里我需要确认一下 **[白话主题]**，因为它会影响 **[业务后果]**。

比如 **[一个真实场景]**。

你们更希望：
A. [选项]
B. [选项]
C. [选项]

如果目前还没定，我建议先按 **[建议]** 来理解，因为 **[一句原因]**。”

不要每次机械套完整模板。问题明显时可以缩短。

## 语言约束

- 避免连续三个以上专业词。
- 必须出现专业词时，紧跟一句白话解释。
- 选项尽量描述“结果”，不要描述“技术实现”。
- 不问“你们用什么数据库/消息队列/协议实现”，除非用户已经进入方案阶段。
- 允许用户只回答“A/B/C”或“按你建议的”。
- 用户回答含糊时，先复述你理解的业务含义，再继续。
